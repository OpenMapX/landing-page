# Landing-page content

The site should help a new visitor understand OpenMapX, try it, and decide
whether to host it. This is a content and information-structure pass. Keep the
existing components, theme, typography, and responsive layout.

The user authorized research, rewriting, verification, and a pull request in
this session. Proceed with the content work without an additional approval step.

## Editorial direction

Use the direct product explanations and practical examples of Immich,
authentik, Nextcloud, and Home Assistant. Follow blader/humanizer's editing
process: identify empty emphasis, rewrite around supported facts, then read
the result again for repetitive structure and unsupported additions.

Prefer a task-led explanation to the existing catalog of implementation terms.
A light copy edit would leave important omissions and overclaims in place.
A visual redesign belongs to the user's separate session.

## Content contract

- Explain search, journeys, map context, saved places, and self-hosting.
- Group the feature catalog around visitor tasks, using the existing cards.
- Add imports, OSM corrections, the optional Dawarich timeline, and useful
  documentation and contribution links.
- Explain account requirements, coverage, external providers, installation,
  offline limits, and self-hosting effort beside the relevant claims.
- Separate implemented capabilities from development ideas. Do not invent
  release dates, distribution status, adoption figures, or performance claims.
- Distinguish open-source software and open datasets from optional commercial
  services. Preserve upstream attribution and the project's license split.
- Review legal prose for factual contradictions and scope. Do not invent
  operator details, contracts, log deletion, or legal conclusions.
- Remove the homepage's placeholder logo image presented as an application
  screenshot. Real product imagery belongs to the later design pass.

## Acceptance

Check public claims against current product code and supporting documentation.
Run the landing package's check, tests, and static build. Inspect all rendered
routes and links, desktop and mobile navigation, metadata, and feeds. Have an
independent Codex reviewer inspect the final changes. Open a PR with evidence
and explicit limits; this work does not qualify product runtimes or deployment.
